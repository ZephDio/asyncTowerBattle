# AGENTS.md

Shared project guidance for all coding agents working in this repository.

Skills and supporting tools live in `.agents/`. See `.agents/README.md` for agent setup and MCP configuration.

## Layout

This is a pnpm workspace with two packages that share their tooling config at the root:
- `client/`: the browser game (Vite, plain TypeScript on a canvas inside a React and Tailwind page shell). The local `@ddd-ts/traits` package is `client/traits`.
- `server/`: asyncTowerBattleServer, a NestJS app on port 6868 that trades boards for opponent boards and holds the player accounts (Google or email or pseudo and password sign-in, sessions, the "first time" steps of each player). It stores them in Postgres (docker compose, Prisma migrations). See `server/README.md`.

Shared at the root: `tsconfig.base.json` (both `tsconfig.json` files extend it), `biome.json`, `devenv.nix`, `pnpm-workspace.yaml`, the lockfile, and the TypeScript, Jest and SWC dev dependencies in `package.json`. Package-specific settings stay in each package: module system (the client is bundled by Vite, the server is Node ESM), `jest.config.json`, `nest-cli.json`.

## Commands

The package manager is pnpm. A devenv/direnv shell provides Node 22 and pnpm; `devenv up` runs both the Vite client and the server as processes. Run commands from the root unless noted.

- `pnpm start`: start the Vite client and the server together. `pnpm start:client` and `pnpm start:server` start one; the server's `start` regenerates the Prisma client and applies the pending migrations first, so a pulled schema change needs no manual step. `pnpm start:infra` starts the server's Postgres in the project's Docker daemon and applies its migrations; the devenv shell starts that daemon on entering the project (`stop-docker` stops it). `pnpm start:client:dev` starts the client and opens it on `/?dev`. The client serves `client/index.html`, which loads the React app `client/src/main.tsx`.
- `pnpm typecheck`: run `tsc --noEmit` in both packages. The VS Code task runs the client's with `--watch`. The shared tsconfig is strict, including `noUnusedLocals`, `noUnusedParameters`, `noUncheckedIndexedAccess`, `noPropertyAccessFromIndexSignature` and `noImplicitOverride`.
- `pnpm format`: run the Biome formatter over `client/src` and `server/src`. It uses tabs, a 120-column line width and double quotes.
- `pnpm test` runs both packages' tests. For a single file, run Jest from the package: `cd client && pnpm exec jest src/shared/hitboxes.spec.ts`. Jest uses `@swc/jest`, roots at each package's `src` and matches `*.spec.ts`. There are very few client tests.
- `pnpm test:integration` runs the server's `*.int-spec.ts` tests against the `atb_test` database (`TEST_DATABASE_URL`) in the running Postgres, which it migrates first. `pnpm test` leaves them out.
- `pnpm build` builds the server into `server/dist` and the client into `client/dist`. `pnpm build:docker` builds the `docker-compose.yml` images from the `Dockerfile` in the project's Docker daemon.
- `docker-compose.yml` at the root runs the whole app (Postgres, the server, and the built client in nginx, which proxies `/api` to the server) for a Portainer stack deployed from the repository; the `Dockerfile` builds both images. It needs `JWT_SECRET`, see the file's header. Vite listens on every interface so players on the local network can join a dev game.
- Running the game: the `atb-game` MCP server (`.mcp.json`, `.agents/mcp/server.py`) keeps the game open in headless Chromium from `.agents/playwright.nix` and starts Vite in `client/` if nothing answers on port 5173. Its tools:
  - `start` begins a seeded game.
  - `state`, `ascii` and `inspect` read the game as JSON or text.
  - `screenshot` captures the page, optionally cropped to a grid.
  - `drag`, `click_cell` and `click_hud` send real mouse events.
  - `give` and `set_gold` set the game up directly.
  - `start_battle` (paused), `step` and `run` control battle ticks.
  - `eval` runs JavaScript in the page.

  The game-testing skill covers using them, including the `.agents/mcp/call.py` fallback for sessions where the tools aren't loaded. The tools call the debug bridge `client/src/debug/bridge.ts`, which the game installs as `window.__atb` when opened with `?debug`. Add new reads or actions there. `python .agents/mcp/smoke.py OUT_DIR` in that Nix shell plays a round through the tools. For one-off screenshots without the server, use `nix-shell .agents/playwright.nix --run "python .agents/scripts/screenshot.py --help"`.

## Client architecture

Paths below are relative to `client/`. This is an async auto-battler played in the browser. The player builds an army on a grid during a shop phase. The army then fights an AI-supplied opponent army in an automatic battle. The code has no framework: plain TypeScript classes render to a 2D canvas.

### Page shell
- `src/main.tsx` mounts the React app in `src/app/`, styled with Tailwind (`src/index.css`, `vite.config.mts`). `App` lays out `GameCanvas` and the `SideMenu` drawer, which floats over the game so opening it never moves the canvas. `GameCanvas` renders the game's container and `<canvas>` and calls `startGame` once. The game itself stays plain TypeScript; React only owns the page around the canvas.
- Before playing, `LoginScreen` asks the player to log in with their pseudo or email and password, register with an email, or use Google (`google-button.tsx`, Google Identity Services), or to play as a guest. `src/auth/` talks to the server's `/auth` routes and keeps the session tokens in localStorage; on load `App` resumes a stored session with its refresh token. Games opened with `?debug` never show the login screen: they resume a stored session, which the game tools' `start(player=...)` puts there, and play as a guest without one. The tutorial opens by itself (`App`, `first-time-steps.ts`): each time a guest starts playing, and for a logged-in player only the first time, which the server keeps in `player_steps` (`GET /players/me/steps`, `POST /players/me/steps/tutorial-seen`); debug runs skip it. Only a logged-in player outside dev mode stores boards on the server and consumes opponents; guest and `?dev` games read opponents for free. The same players have their game saved on the server (`engine/saved-game/`, the `/current-game` routes): `Game` saves at the start of each shop and each battle, and once logged in `App` tells the game to load the saved game, which the main menu offers with a Continue Game button in place of Start Game (`Game.resume` reopens the shop, or the battle against the saved opponent), and a Concede button under it that deletes the saved game. Each run has a seed (`Game.runSeed`, drawn on Start Game and saved with the game): the shop offers, each round's environment and the seed of the player's published board are drawn from it through `runRandom` (`shared/run-random.ts`, one stream per step), so a continued run offers the same things. Battle randomness still goes through `BattleRandomSeed`. A guest or `?dev` game saves nothing.
- `MouseEventHandler` listens for presses on the game container only, so clicks on the page shell never reach the game, and for moves and releases on the whole window. Canvas page coordinates come from `CanvasRenderer.pageOrigin()`.

### Top-level loop
- `startGame` in `src/index.ts` wires up `GameWrapper`, `CanvasRenderer`, `InputToIntent` and `MouseEventHandler`.
- `GameWrapper` (`src/engine/wrap.ts`) switches between `MainMenu` and `Game`.
- `Game` (`src/engine/game.ts`) runs the phase cycle `ShopPhase` → `Battle` → `BattleSummary` → shop again. Only one phase field is non-null at a time. The player has `MAX_LIVES` (5) lives and loses one per defeat; a run lasts at most `MAX_ROUNDS` (16) rounds (both in `src/engine/game-rules.ts`, which also holds `STARTING_LIVES`, lowered to 1 to test the end of a run quickly). It ends at 0 lives or after the last round's summary, then a last phase, `RunResume` (`src/engine/run-resume/`, field `runResume`), shows a parchment with lives, wins and round around the read-only army board (descriptors still work) and a Continue button back to the main menu. `RenderableState.backdrops` holds what is drawn under the grids, as that parchment. Opponents come from `RemoteMatchMaker`, which POSTs the player's serialized board and win/loss record to the server (`server/`) and gets an opponent board back. When the server is unreachable it falls back to `LocalMatchMaker`, which keeps hard-coded enemy armies per round in `src/engine/match-maker/`.
- `Battle` ticks the `Battlefield` with `setTimeout` at 32 ticks per second. Battle randomness must go through `BattleRandomSeed` so battles stay deterministic, and randomness of the shop or the environment through `runRandom` so a run stays reproducible. `src/shared/seconds.ts` converts between seconds, frames and cast speed.
- Rendering is pull-based. `CanvasRenderer` calls `gameWrap.getRenderState()` every frame. The active phase returns a `RenderableState`, which is a list of grids with their drawables plus free renderables. Drawables are sorted by `drawPriority` and then by y position.
- Game coordinates are y-up: in `Cell` and `GridPosition`, y + 1 is the cell above on screen (`Cell.up()`), so "below" means negative y in grid shapes, pattern cells and hitbox offsets. The game keeps its own position frame and `TDrawable.getCanvasPosition` (`src/shared/traits/render/drawable.ts`) converts it to y-down canvas coordinates only when drawing.
- Input goes from `MouseEventHandler` to `InputToIntent`, which uses `instanceof` to find the active phase and picks a per-phase translator in `src/control/translators/`. A translator hit-tests the screen position and calls methods on the phase object directly.

### Traits system (most important concept)
Almost every entity is built from mixins using the local `@ddd-ts/traits` package (`traits/traits.ts`, linked as `file:./traits`).
- `Trait(base => class ...)` defines a mixin. `Subtrait([deps...], base => class ...)` defines a mixin that requires other traits.
- `class X extends Derive(TraitA, TraitB(args), ...)` composes traits. Constructor props are the intersection of every trait's props.
- `implementsTrait(obj, T)` is the runtime check and `ImplementsTrait<typeof T>` is the instance type. `Any*` aliases such as `AnyBattleTower` are defined this way.
- Naming: a `T*` trait carries its own data, and some are factories that take config, e.g. `TImageDrawable(img, size, priority)` or `TBaseStats({...})`. An `HT*` trait ("holder") delegates to another object passed as a prop, such as `hitboxHolder`, `imageDrawable`, `statsHolder` or `descriptor`. This lets a recruit or battle entity reuse its blueprint's hitbox, image and stats.
- Engine traits live in `src/shared/traits/engine/`: core collision and grid traits, casting, recruiting, status, synergy and tags for alignment, biome, building and species. Render traits live in `src/shared/traits/render/`.

### Three-layer entity model
Each game piece type (units, towers, totems, barracks, castle, tiles, projectiles) has parallel folders, usually `blueprint/`, `recruit/` and `battle/`, each with an `implementation/` subfolder:
1. **Blueprint**: the shop and catalog definition. It holds price (`TShopBlueprint`), rarity (`TRarity`), hitbox, image, description, `TBaseStats` and the `type` tag. `toRecruit(cell)` creates the recruit.
2. **Recruit**: the owned piece placed on the player's `ArmyGrid` or `Inventory`. It holds a cell and handles drag and drop through `moveRecruit`. Pieces cannot be rotated: a recruit always uses its `gridShape` cells and `patternEffect` cells as written, facing the player. `toAllied(grid, hooks)` and `toEnemy(grid, hooks)` create the battle entity. Every grid element carries a `BoardOrientation` enum (`Normal` or `Mirrored`, `src/shared/traits/engine/core/board-orientation.ts`). The enemy version has its anchor cell flipped with `BattleGrid.flip` and is built `BoardOrientation.Mirrored`, which negates its footprint and pattern and draws its single front-view image rotated by π. The opponent board is a point mirror of the board its builder made: a top right effect becomes bottom left.
3. **Battle**: the live combat entity. It is built from `HaveStats` and `Caster` and implements `tick()` and `onCastResolve()`.

The castle is the exception: it is not a grid element. `ArmyGrid` keeps it apart (`castle`, placed through `setElement`) and `engine/castle/castle-geometry.ts` places its 3-cell-tall sprite mostly off the board, overlapping the carpet by a quarter cell (Dwarf) or half cell (Elf), left of the top row (right of it, mirrored, on the opponent's board). The path ends on the top left cell (`getCastleEntryCell`), leaves it by its left edge (the castle's door), The castle block has two doors: `doorPosition` on the top left cell's left edge, where enemy units arrive, and `spawnPosition` one cell higher, where its own units spawn and enter the opponent's board (mirrored: the right edge of the enemy's top right cell). The path's start, the top right door cell, is entered from its right edge. `BattlePath` runs units from the other castle's spawn point through the path to the castle's `doorPosition`. A board stored before this change has no tile on that cell: `deserializeBoard` adds it.

Adding a new piece usually means one file in each layer's `implementation/`, plus updates to the layer's union type (`Any*`), its fixtures and builders (`*-fixtures.ts`), and its image entries in `src/renderer/resources/*.resources.ts`. Images are served from `public/resources/`; each piece has a single front-view image, `<piece>.png`.

A piece can be gated behind a science (`src/shared/traits/engine/science.ts`): the blueprint adds `TRequiresScience(Science.X)` and `RetailFiller.candidates` leaves it out of the offers (and of the refresh bell) until the army holds that science. The army holds a science when one of its pieces grants it: a blueprint adds `TGrantsScience(Science.X)` and its recruit takes `HTGrantsScience` (`scienceHolder: blueprint`), as the castles do. `Army.sciences` is derived from the castle and the grid pieces each time, so nothing is stored or serialized. The shop shows the held sciences on the ribbon right of the reserve, and a battle shows each army's beside its banner (`src/shared/hud-element/science-hud.ts`, art from `scripts/generate-science-ribbon.py`). A seal opens the science's scroll (`science-panel.ts`), which lays the pieces the science unlocks on an invisible `ScienceGrid`; `ShopInputToIntentTranslator.handleSciences` routes the seals and the scroll before the rest of the shop. A descriptor shows the seal of each science its piece grants.

### Cross-object communication: hooks
Entities never hold references to the army or battlefield. Instead they receive hook objects, which are bags of callbacks: `BattleArmyHooks` (`src/engine/army/battle/battle-army.ts`) provides target search, `addProjectile`, allied and enemy food, gold and buff hooks, and grid hooks. The shop uses `TokenHooks` and `shopPhaseHooks`. Wire new interactions through these hooks.

### Other subsystems
- `src/engine/stats/`: `Stats` covers health, attack, speed, cast and attack speed, food cost, range, conditions and boons. Statuses (frozen, rooted, stunned, stone shield, etc.) are in `status/`. `BaseStats` holds the blueprint values. `setModifier(stat, source, percent)` and `clearModifier` keep one percent per source and stat (not max health): positive ones add to `basePercentStat`, negative ones each multiply the stat. Slows such as `BoggedDown`, `Hindered` and `Frozen` use them.
- `src/engine/grid/`: `ArmyGrid` (shop), `BattleGrid`, `RetailGrid` (shop offers) and `Inventory`. They share the `TGrid` trait and handle element placement and validation.
- `src/engine/pattern-effect/` and the `TSynergy` trait: adjacency and pattern synergies between pieces on the grid.
- `src/engine/target-zone/` and the `TTargeting` trait: towers find enemies in a set of cells relative to their anchor (`TargetZone`), not within a distance. The default is the 8 cells around the tower. The shop shows each target cell as a bow, red when it holds a path tile and grey otherwise (`ArmyGrid.addTargetTiles`).
- Economy: gold (`src/engine/gold`) is spent in the shop and food (`src/engine/food`) is consumed by casts during battle.
- Reserved offers: right-clicking an offer toggles its reservation (`OfferReservations`, `engine/shop/retail/offer-reservations.ts`). `Retail.refresh` keeps reserved offers in their slot and draws new ones in the others, on the refresh bell and in the next round's shop: `Game` hands the same reservations to each `ShopPhase`, and buying an offer clears its reservation. `Game` saves them with the game (`SavedGame.reservedOffers`, optional for games saved before), so a continued run keeps them; they are not sent with the board. A reserved offer shows a `RESERVED` wood sign (`ReservedSignHud`).
- HUD elements are in `src/shared/hud-element/` and the screen-percentage helpers (`PercentToReal`, etc.) are in `canvas-renderer.ts`.
- Wooden signs: `drawWoodPanel` (`shared/traits/render/wood-panel.ts`) draws the plank panel the same way from `public/resources/hud/wood-panel/` (`scripts/generate-wood-panel.py`), its frame outside the given area, at the army banner's art pixel (0.2 screen units). `drawWoodSign` adds a label: `ShopSignHud` and `ReserveSignHud` (above the reserve grid) use it.
- The descriptor (`DescriptionHud`) hangs from a scroll like it, `drawDescriptorScroll` (`shared/traits/render/huds/descriptor-scroll.ts`, art from `scripts/generate-descriptor-scroll.py` in `public/resources/hud/descriptor-scroll/<rarity>/`), but its rolls carry text and the top one has dark wood handles sticking out of its sides: the title in the top one, up to 4 tags (2 per row) in the bottom one; its box is fixed, from level with the start button to just above the reserve sign, the bottom roll always holding two rows of tags. Common, uncommon (green vines in the margins, a green nail), rare (denser blue vines with berries and diamonds) and epic (purple vines with gold berries, curls and framed gems, a gold line inside the borders, a faceted gem set on each roll end and gilded tendrils sticking out of the footer) are drawn, and legendary (red and orange flame vines with yellow embers and a gold-framed ruby diamond, two ruby gems on each roll end, a prestigious red flame plant with a gold flower around a ruby bud sticking out of the footer, a crest of gold flames over the header, gold-and-yellow rod tips), each rarity adding to the previous one. The tutorial panel is drawn on the small tooltip scroll instead (`HudTooltip.drawScroll`, nine pieces from `scripts/generate-scroll.py`).
- Stretchable art: `HudTooltip.drawScroll` (the parchment of the tooltips, the science panel and the run summary) draws nine pieces from `public/resources/hud/scroll/`, made by `scripts/generate-scroll.py`: the corners keep their size, the edges are 1 pixel strips that repeat and the center is a tile. The grids' grass is laid out by `engine/grid/grass-layout.ts` from the run's seed (`GrassSeed`, set by `Game`) in patches of 1 to 4 cells drawn from `public/resources/environment/grass/` (`scripts/generate-grass.py`): every patch is flat green at its border, so any two join. Serve new files of `public/` to Vite by restarting it.
- Icons: the pixel icons live in `public/resources/icons/`, drawn by `scripts/generate-corn.py`, `generate-gold-coin.py`, `generate-heart-container.py`, `generate-buff-icons.py` (16x16) and `generate-pattern-stars.py` (the 24x24 synergy stars). The same icons replace emoji in canvas text: `scripts/generate-icon-font.py` builds `public/font/icons.ttf` (a color font) and `icons.css`, which adds it to the `text` and `title` families for those emoji only. Write descriptions with 🪙 (gold), 🌽 (food), ❤ / 🖤 (castle health, full and empty), 🥾 (unit speed), 💚 (unit health), 🗡️ (unit castle damage, the bomb), ⚔️ (tower projectile damage), 💠 (tower cast speed), ▣ (a synergy cell, the yellow star) and ☆ (the grey, unmet synergy star). Buffs a piece grants to the whole army use the shield icons in `public/resources/icons/army-buff/` (built by the layering-design skill): 👢 (army unit speed), 💖 (army unit health), 🏹 (army tower projectile damage) and 🔮 (army tower cast speed), while 🥾 💚 ⚔️ 💠 stay for the stat rows of a unit or tower. After changing an icon or the emoji map, run `pnpm generate:icon-font` in `client/`. The full catalogue is in `docs/emoji-icons.md`.
- Fonts: the digits of `public/font/text.ttf` and `title.ttf` are pixel glyphs from x10y12pxDonguriDuel (hicc), merged by `scripts/merge-digit-font.py` (`pnpm generate:digit-font`). Setup, credits and license are in `docs/fonts.md`.
